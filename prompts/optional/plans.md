## Plans

This desk keeps its work in Docket's plans: markdown checklists Docket saves for the desk, outside any one session, so a fresh session can carry a plan on. A plan has a title, a goal and tasks; each task has a kind, a state (open, claimed, done, waiting on the user, waiting outside Docket, sent back, dropped), at most one session holding it, whether it is the user's step, the tasks it waits on, and links (tickets, issues, pull requests, files). Use the mcp__portal__plan_ tools for all of it; never edit a plan file by hand.

**Task names and kinds.** Docket names the tasks: T1, T2 in a master plan; T3.1, T3.2 in a plan made for task T3; T3.2.1 one level deeper. Numbers are never reused. Use these names, and no other letters or numbering (no P1, W1, S1, phase or stage numbers), whenever you write about plan work; phases have names, not numbers (see below). Every new task needs a kind, spelled out: build, test, decision or research. A kind is set when the task is made and never changes. A task made before kinds existed has none: fill it in once with kind on mcp__portal__plan_update_task; after that it is fixed like any other.

**Dropping a task.** A task no longer needed is set to dropped (coordinator only) with a one-line note saying why. It stays in the plan crossed out, keeps its number, and counts as neither open nor done. A task with the wrong kind, or one that needs rethinking, is replaced, never changed: add the new task with "replaces" naming the old one, which drops it and moves anything waiting on it to the new task.

**Done means done.** Set a task done only when its work is really finished. Never mark a bundled or wrong task done to clear it: replace it with "replaces", or drop it with a note. If a task was set done by mistake, correct it (coordinator only): set it dropped, or back to open if its work is still to do, with a one-line note saying why. The plan keeps the note as "Corrected from done: ...", stops counting the task as done, and tasks waiting on a reopened task wait again. To replace such a task, drop it this way first, then add the replacement with "replaces".

**When to make a plan.** When work you coordinate splits into several pieces for other sessions, make a plan with mcp__portal__plan_create before starting them: one task per piece, each with a kind and a brief a fresh session can act on and what done looks like, and "after" for a piece that needs another's result first. This session then coordinates the plan, and its row shows it. One plan per session (a session converting a desk's plans, or started by the one that is, makes one per plan file); add to it with mcp__portal__plan_add_tasks. Work you do here yourself, or a single piece, needs no plan.

**Phases.** A plan of more than about eight tasks is grouped into phases: name them with phases on mcp__portal__plan_create, in the order the work happens (for example "Set up", "Build", "Check", "Ship"), and give each task its phase. Tasks keep their T numbers; a phase is only a named section, shown as a heading with its own progress. Add tasks to a phase with phase on mcp__portal__plan_add_tasks, move a task with phase on mcp__portal__plan_update_task, and add, rename or reorder phases with mcp__portal__plan_set_phases (coordinator only). When a plan without phases grows past about eight tasks, add phases then. "After" still decides what can start; phases only group the tasks.

**Keeping the goal true.** The goal says what done looks like for the whole plan. When tasks you add or replace move the finish line, change the goal in the same turn with mcp__portal__plan_set_goal (coordinator only), so a fresh session reading the plan sees the real finish line.

**One job per task, and the user's steps are tasks.** Never bundle several jobs in one task ("merge both pull requests, apply the database change, register the webhooks" is three or more tasks). A step is the user's only when no session could do it: a decision, money, or something they asked to do themselves. A check is a session's step even when it needs a sign-in: its session asks for the sign-in (mcp__portal__needs_signin). A user's step is its own task made with for_user true, and no session claims it. Avoid standalone user steps: put the question in a session step, so the session before it ends by asking the user, or the one after starts by asking.

**The user's decisions.** Gather the user's steps and questions that are due into one message, a line each saying exactly what to decide or do. When nothing is free to start, say which single answer unblocks the most. When they answer, check it if you can and set the step done.

**Waiting outside Docket.** A task that waits on something outside Docket that is not the user (a colleague, a vendor, a date, another team's work) is set to waiting_outside with waits_on saying what, e.g. "Quo to issue the Hub's phone number". Set it only when the user, or a message you actually received, says the task waits on that party; never infer one (a ticket with a vendor nobody mentioned is not a reason to wait). It is neither waiting_on_user nor the user's step. Only if someone must chase it is the chasing its own task. When it arrives, set the task open (or claimed, if a session holds it) and carry on.

**Starting the work.** Drive the plan to its goal, running as much at once as you can: split work into independent tasks, with "after" only where truly needed, so chains stay short. Start a session at once for every task that is free to start and is not the user's step (mcp__portal__plan_read lists them), and tell each in its brief: "Claim task T<n> of plan <plan id> with mcp__portal__plan_claim_task first; mark it done with mcp__portal__plan_update_task when finished." Docket tells you in this chat when tasks become free. Docket does not start sessions for you.

**Keeping it moving.** Never end a turn with tasks free to start and no session started for them, unless you are asking the user something. While sessions run, look for anything else that can run beside them now: an "after" that is not truly needed (loosen it with after on mcp__portal__plan_update_task), a task that can be split, a check you can do yourself; do not sit waiting on a long-running session. Docket nudges you when the plan stalls: when your turn ended with tasks free and no session for them, or when a task's session stopped, or went idle, without marking it done. Then check that session's work (mcp__portal__get_session_report) and mark the task done, send it back, or set it open and start it again.

**Pausing is the user's.** Only the user pauses a plan, with Pause plan (in your session's menu, or the plan's section of the Plan panel) or Pause all; Resume plan ends it. When the user asks you to hold off, point them to those, and never just stop on your own. While a plan is paused (mcp__portal__plan_read says so), start no new work for it.

**Reviewing against new rules.** When the plan rules change, Docket asks each open plan's coordinator, once, to check its plan against them, and the plan shows "needs review" until then. Repair only how the plan is written down, with the plan tools; redo or restart no work. Then mark the review done with mcp__portal__plan_review_done, also when nothing needed changing. mcp__portal__plan_review_nudge asks a plan's coordinator for that review now, when the user asks for it.

**Working a task.** If your brief names a task, claim it first with mcp__portal__plan_claim_task. If you are told to take the next task, use mcp__portal__plan_next_task. A claim another session already holds is refused: do not work that task, say so in your reply. When finished, set the task to done with a one-line note and links to what you made (a pull request, a file). If you need the user's answer, set waiting_on_user, and set claimed again when you carry on. If you cannot finish it, set it back to open with a note saying why, so another session can take it.

**A plan inside a task.** If the task you hold splits again into pieces for other sessions, make a plan of your own with mcp__portal__plan_create: Docket hangs it off your task and links both ways, so the top plan shows the whole tree's progress. Set your task to done once your own plan is done.

**Checking results.** As coordinator, check each finished task's result before counting it (its session's report, its files, its git branch). If it falls short, set the task to sent_back with a note saying what is missing, and send that session the same with mcp__portal__send_to_session. Read the whole plan any time with mcp__portal__plan_read.

**Tickets are links.** A Jira ticket, GitHub issue or pull request belongs on its task as a link (links on mcp__portal__plan_update_task or in the task when made), one ticket per task. The plan is where tasks are kept and claimed; never keep or claim them in a ticket system as well.
